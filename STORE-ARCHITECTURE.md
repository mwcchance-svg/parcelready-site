# ParcelReady store architecture

Ruled by Matt via HQ, Nov 22, 2026. This supersedes the Gumroad checkout
route in the original website brief for everything except the 13 existing
products.

## Why

The catalog is not 60 products. It is 60 data lines multiplied by every
metro: Houston HVAC, Dallas HVAC, Mansfield HVAC, and Midlothian HVAC are
four separate purchasable datasets, and the full grid runs to hundreds.
Gumroad listing creation is manual and rate limited by hand; it cannot
carry this catalog. Purchases happen on parcelreadydata.com.

## Shape of the store

- Front end: the static site in this folder (GitHub Pages, $0), unchanged
  in structure. Pack pages render from catalog.json as before.
- Store brain: a Cloudflare Worker (worker/ in this folder) on the free
  tier. It is the only moving part, and it holds all secrets. The static
  pages never see a secret key.
- Money: Stripe, ParcelReady's own account, completely separate from Page
  Harbor Studio's account and from Daniel Reeve's (the Daniel Reeve
  precedent: one account per venture). Products and prices are created
  programmatically from the pack registry by scripts/stripe_sync.py, so a
  newly verified metro pack becomes purchasable the day it verifies, with
  no manual listing step and no daily cap.
- Files: pack files live in a Cloudflare R2 bucket (free tier) under keys
  matching the registry's delivery_file names. Buyers never get a public
  link; delivery is a signed, expiring token minted per purchase.
- Registry: catalog.json is the registry of record on the site side. Relay's
  pack registry is the upstream source; a pack enters catalog.json at
  verification time with store.mode "stripe" (new packs) and its
  delivery_file name. The 13 existing products carry store.mode "gumroad"
  and keep selling on Gumroad as a feeder shelf; the sync script skips
  them, and their pack pages keep the Gumroad buy route.

## Flows

### Purchase (one time packs)
1. Buyer clicks Buy on the pack page. The page posts the pack id to the
   Worker's /api/checkout.
2. The Worker looks the pack up in store-registry.json (generated by
   build.py from catalog.json), creates a Stripe Checkout Session for the
   pack's synced price id, and returns the session URL.
3. Buyer pays on Stripe's hosted page. Stripe redirects to the site's
   thanks page.
4. Stripe's webhook calls /api/webhook. The Worker verifies the signature,
   and on checkout.session.completed it mints a delivery token (72 hours,
   bound to the pack and the buyer's email), stores it in KV, and emails
   the buyer the download link from the ParcelReady domain.
5. /api/download validates the token and streams the file from R2.

### Membership (Dallas Code Cases today; the pattern for refresh packs)
- The pack's price is a Stripe subscription price (Stripe Billing). The
  sync script creates it as recurring monthly.
- checkout.session.completed delivers the current file as above.
- On every invoice.paid (each renewal), the Worker delivers the current
  refreshed file again, so members receive each refresh cycle's file by
  email without logging in anywhere. Relay's refresh updates the R2 object
  and the pack's data_as_of in the registry; the next invoice.paid picks
  the new file up automatically.

### Free sample (every pack page, and the sample request form)
- The sample is delivered by email capture on our own site, replacing the
  Gumroad sample download on site pages. The form takes business name and
  email (plus trade, state, metro, and reply route on the request form).
- /api/sample stores the lead in KV for Herald's follow up list, sends a
  notification copy to hello@parcelreadydata.com, and emails the requester:
  the sample file link when the pack exists, or a confirmation that their
  state and category are in production or queued when it does not.
- The viewable sample explorer stays on the pack page; capture gates the
  file, not the inspection. That keeps the inspect-before-you-buy promise
  while building Herald's list.

### New pack day (Relay verification to purchasable)
1. Relay verifies the pack; its files land in data-products and R2.
2. One catalog.json entry is added (store.mode "stripe", price,
   delivery_file, data_as_of, sample source).
3. build.py regenerates the site and store-registry.json.
4. stripe_sync.py creates the Stripe product and price (idempotent; it
   finds by registry metadata first) and records the ids.
5. One commit deploys the site; the pack is purchasable the same day.

Admin upload route (HQ sanction, Nov 23, 2026): POST
/api/admin/upload, gated by the same admin token as the sync route,
writes delivery files to the bucket with the service role, restricted
to packs/ and samples/ keys and CSV payloads. With the token set, the
landing pipeline runs end to end from Mason's desk (check, build,
upload, redeploy); the window is touched only for the function paste.

## Sales tax: RULED by Matt, Nov 23, 2026 (wiring built the same day)

Prices are tax-inclusive: the sticker is the whole price, nothing is
added at checkout, and the tax engine carves the correct buyer-state
tax out of the sticker wherever ParcelReady has nexus. Today that is
Texas only; other states switch on as their economic thresholds cross
(flag 3 below stands as the monitoring rule). The Texas sales tax
permit is Matt's own item, coming soon; he ruled it does not gate the
wiring or the launch.

- Mechanism: Stripe Tax in inclusive mode. The function runs with
  TAX_MODE "stripe_tax"; checkout sessions enable automatic tax and
  require the billing address (the buyer's state places the sale), and
  prices are created with tax_behavior inclusive.
- Category: Stripe tax code txcd_10701300, Website Data Processing,
  per Matt's data-processing treatment (Texas taxes data processing
  services with a 20 percent exemption). The alternative determination,
  Electronically Delivered Information Services (txcd_10701410), is a
  one-constant flip in the function if the CPA lands there.
- Pre-ruling prices: the sync never silently reuses a price that lacks
  inclusive behavior once tax is on. It creates the inclusive price and
  archives every other active price on the product (Stripe prices
  cannot be deleted), so exactly one live price per pack remains.
- FLAG 3 (standing): Economic nexus in other states as the national
  catalog sells. Threshold monitoring belongs in the monthly books
  pass once revenue exists; a state switches on by adding its Stripe
  Tax registration, no code change.

## Matt's rulings folded in (Nov 22, 2026, evening)

1. METRO DEFINITION. A metro is the service area the way buyers work it,
   not a county line. Dallas Fort Worth carries the full MSA county list;
   Houston and the Austin to San Antonio corridor are defined the same
   way in catalog.json's metros table. The browse order is state, then
   metro, then pack: state hubs link metro hubs
   (states/<state>/metros/<metro>/), and every pack page states its
   coverage and its metro. Membership is sold by metro; the state tier
   (every metro in the state) is the step up, priced in the pricing
   architecture (Texas absentee statewide $199).
2. FRESHNESS DISPLAY. Every pack page and card shows the exact pull date
   paired with its refresh schedule from REFRESH-SYSTEM.md (monthly for
   code cases; quarterly plus a January close-out for permit digests;
   monthly plus the post-certification rebuild for county appraisal
   records; monthly full re-verification for lead packs; every cadence inside Matt's 30 day cap). One registry
   field per pack (refresh_schedule); Relay's refresh rolls data_as_of
   and the pairing updates everywhere in one rebuild.
3. SAMPLES. The free sample is a fixed percentage of each dataset, the
   same share catalog wide: sample_percent in catalog.json, set to 10.
   build.py draws it systematically (every Nth row) from the full file,
   stages the delivery CSV under delivery/samples/ for R2, and the pack
   page states the share and the counts in words. The delivered sample
   conforms to the recorded spec's floor and ceiling: 10 percent, floor
   15 rows, ceiling 50 (Relay's confirmation, Nov 22, 2026). The on page
   explorer is a preview mechanic and may show more rows than the
   delivered file; its count line says so in words. This supersedes rule 6 of PRICING-ARCHITECTURE.md (a flat
   15 rows); that file is Relay's to correct.
4. PRICING PRESENTATION. Every pack page carries a two ways to buy block:
   the full dataset first (one time price, data as of date, and the plain
   statement that a one time file does not update itself), and beside it
   the stay current membership at the pricing architecture's figures
   (pack price per quarter for standard lines; $79 a month for the fast
   moving code cases line), framed against re-buying: quarterly
   memberships are stated as their monthly equivalent against the cost of
   re-buying the set at the next refresh, and the monthly line is stated
   as holding the current file for the price of one snapshot a month. No
   discount is claimed that the architecture's numbers do not carry.

## Format choice: CSV and XLSX (Nov 23, 2026, Atlas's ruling for Matt)

Buyers get the format choice on the store that the Gumroad listings already carry. Every pack and every delivered sample stages as a format pair: the CSV and an XLSX sibling with identical rows (scripts/make_xlsx.py converts in the shelf's conventions: one sheet named "Sheet", every value stored as text exactly as the CSV carries it, so ZIP codes and account numbers are never re-typed as numbers). The landing pipeline gains the pair as a hard gate: scripts/pack_check.py fails a pack whose delivery pair or sample pair is incomplete or whose row counts differ across formats, and the bucket step uploads both objects (packs/<name>.csv and .xlsx, samples/<name>.csv and .xlsx).

The delivery token serves both formats: /api/download with no format parameter serves the CSV (every link already in a buyer's inbox works exactly as before), and &format=xlsx on the same token serves the XLSX sibling with the spreadsheet content type. The purchase and sample emails offer both downloads as two buttons with both raw links, inside the existing branded design, and the copy notes plainly that the CSV opens straight into Google Sheets; no third Sheets file exists. The admin upload route accepts .xlsx keys beside .csv and stores the correct content type per extension.

Retrofit of the live twelve, Nov 23, 2026: the three lead packs already carried XLSX siblings from their original builds (verified by the pair check); XLSX siblings were generated and pair-verified for the other nine packs and for all twelve delivered samples. The function side ships in the 35,526 byte build; the bucket uploads of the 21 new XLSX objects run immediately after that build is pasted, because the live upload route still rejects .xlsx keys until it is.
